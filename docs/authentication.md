# Authentication and authorization (LM-052)

LedgerMesh signs people in with their email address only. There is no secret for a person to choose, remember, store or reset: a sign-in proves control of a mailbox by using a single-use link sent to it. The guest demo stays open to everyone without signing in.

The Identity Service (`services/identity`, port 8005) owns everything described here, in its own `identity` database ([ADR-001 §16](architecture/ADR-001-ledgermesh-architecture-and-correctness.md#16-addendum-2026-11-27-identity-service-lm-052)). Its HTTP contract is [`libs/contracts/openapi/identity.v1.yaml`](../libs/contracts/openapi/identity.v1.yaml).

## Flow

```text
Browser                         Identity Service                    Mailbox
  | POST /v1/auth/login-requests {email}  |                            |
  |-------------------------------------->| validate + normalize       |
  |                                       | rate-limit (IP, email)     |
  |                                       | upsert user, revoke old    |
  |                                       | link, store sha256(token)  |
  |<-------------- 202 (always the same) -|                            |
  |                                       |-- email (after response) ->|
  | open https://…/v1/auth/verify#token=… (fragment never sent)        |
  |-- GET /v1/auth/verify --------------->| static confirm page        |
  |<--------------------------------------|                            |
  | press "Sign in"                       |                            |
  |-- POST /v1/auth/verify {token} ------>| atomically consume token,  |
  |                                       | create session, audit      |
  |<-- 200 + Set-Cookie: lm_session=… ----|                            |
  |-- GET /v1/me (cookie) --------------->| resolve + slide idle expiry|
  |-- POST /v1/auth/logout (cookie) ----->| revoke session row         |
```

| Method | Path | Who | Result |
|---|---|---|---|
| `POST` | `/v1/auth/login-requests` | anyone | `202` with one fixed message, `422` invalid address, `429` rate limited |
| `GET` | `/v1/auth/verify` | anyone | Static HTML confirm page; consumes nothing |
| `POST` | `/v1/auth/verify` | anyone | `200` + session cookie, or one generic `400` |
| `POST` | `/v1/auth/logout` | anyone | `204`; revokes the session if there is one |
| `GET` | `/v1/me` | user | Current user and role, else `401` |
| `GET` | `/v1/sessions/introspect` | user | Principal for a forwarded cookie (for the web BFF), else `401` |
| `GET` | `/v1/operator/auth-events` | operator | Auth audit trail; `401` guest, `403` user |

All errors are `application/problem+json` with a `urn:ledgermesh:identity:*` type. `POST` endpoints accept only `Content-Type: application/json` (`415` otherwise). Every `/v1/` response is `Cache-Control: no-store`.

## Roles

| Role | How | Can |
|---|---|---|
| guest | no valid session cookie | use the guest demo, request a link, verify a link |
| user | valid session | everything a guest can, plus `/v1/me` and future saved/personal features |
| operator | valid session **and** the normalized address is in `IDENTITY_OPERATOR_EMAILS` | everything a user can, plus privileged routes such as `/v1/operator/auth-events` |

The role is computed on every request from the allowlist, so removing an address from it revokes operator rights immediately; there is no role column to forget. FastAPI routes use `require_user` / `require_operator` from `services/identity/app/authz.py`.

**No other service requires authentication in this change.** Wallet, Catalog, Coordinator, Audit Ledger and the guest demo behave exactly as before. When a feature needs a signed-in person, the web BFF forwards the browser's `Cookie` header to `GET /v1/sessions/introspect` and acts on the returned `user_id` and `role`; no service reads the identity database (ADR-001 §2).

## Tokens and sessions

| | Login link token | Session id |
|---|---|---|
| Generated by | `secrets.token_urlsafe(32)` (256 bits) | same |
| Stored as | SHA-256 hex in `login_tokens.token_hash` | SHA-256 hex in `sessions.session_hash` |
| Lifetime | 15 min (`IDENTITY_LOGIN_TOKEN_TTL_SECONDS`) | idle 30 min, absolute 12 h |
| Single use | `UPDATE … WHERE consumed_at IS NULL AND revoked_at IS NULL AND expires_at > now RETURNING` | revoked on logout or on the next sign-in in the same browser |
| At most one | partial unique index `ux_login_tokens_one_active`: a new request revokes the previous link | – |

A plain SHA-256 is enough because the input is random and unguessable; a slow hash only matters for low-entropy secrets people choose.

The session cookie is `lm_session=<id>; HttpOnly; SameSite=Lax; Path=/; Max-Age=<remaining absolute lifetime>`, plus `Secure` whenever `LEDGERMESH_ENV` is not `local` or `test` (an unset variable counts as deployed). It has no `Domain`, so it is host-only. Every authenticated request slides the idle expiry forward, but never past the absolute expiry.

## Threat model

| Threat | Mitigation |
|---|---|
| Account enumeration | `202` with an identical body and headers for new and existing addresses; the same code path (upsert) for both; email is sent after the response so SMTP timing does not leak; the per-email limit is checked before any user lookup; one `400` body for unknown, expired, used and revoked links. |
| Token leaks through logs, proxies, `Referer` or history | The token is in the URL **fragment**, which browsers never send to a server. The confirm page strips it with `history.replaceState`, sends `Referrer-Policy: no-referrer`, and uses a strict hash-based CSP. Validation errors name fields but never echo values. |
| Link scanners and prefetchers using up the link | `GET /v1/auth/verify` is a static page. Only the button's `POST` consumes the token. |
| Replay and races | The conditional `UPDATE … RETURNING` lets exactly one of any number of concurrent requests win (tested with 10 threads on PostgreSQL). |
| Brute-forcing tokens | 256-bit tokens, plus the per-IP verify limit. |
| Database theft | Only hashes of tokens and session ids are stored. |
| Session fixation | Every sign-in creates a new random session id and revokes any session the browser presented. |
| CSRF / login CSRF | `SameSite=Lax`, and JSON-only `POST`s: a cross-site HTML form cannot send `application/json`, and no CORS is configured, so a cross-site script cannot either. |
| XSS stealing the session | `HttpOnly` cookie; the confirm page writes only with `textContent`. |
| Mail bombing / flooding | Persistent per-IP and per-email limits (below). |
| Lockout by a third party | **Accepted, and not bounded in time.** Anyone who knows an address can keep it from signing in for as long as they keep sending requests: (1) every login request for the address revokes its pending link (one active link, below), so one request every few minutes, well under the per-email limit, keeps the emailed link invalid without ever getting a `429`; (2) sending the per-email limit at the start of each window keeps the address at `429`. Each request still costs the attacker a request against their per-IP limit and is audited as `login_requested` (with client IP) or `rate_limited`, so an operator can see it in `/v1/operator/auth-events`; mitigating it further (per-email cooldown, several valid links per user) is a follow-up. |

## Policy choices

**Validation is not ownership.** The `email-validator` library checks syntax server-side; anything the browser checks is a convenience only. An address is only known to belong to someone after a link sent to it is used, which sets `users.email_verified_at`.

**Normalization.** Surrounding whitespace is stripped and the whole address is lowercased, so `Alice@Example.COM` and `alice@example.com` are one account (enforced by `uq_users_email` and the `ck_users_email_normalized` check). Dots and `+tags` are **not** folded, because that would merge distinct mailboxes at providers that do not ignore them. Quoted local parts, IP-literal domains, internationalized local parts and special-use domains (`.local`, `.test`, `localhost`) are rejected; internationalized domains are stored in ASCII (IDNA) form; the maximum length is 254.

**Deliverability.** DNS MX checks are **off** by default (`IDENTITY_EMAIL_CHECK_DELIVERABILITY=false`): they add latency and a DNS dependency, and the link already proves deliverability. Turning them on rejects domains that cannot receive mail with the same generic `422`.

**Disposable domains.** No list is bundled, because any list goes stale and blocks legitimate users. `IDENTITY_BLOCKED_EMAIL_DOMAINS` is an optional comma-separated denylist (subdomains included) that returns the same generic `422`.

**One active link.** Requesting a new link revokes the previous one, so an older email (forwarded, or left in a shared inbox) can no longer sign anyone in. The cost is the lockout described in the threat model: a third party who requests links for an address also invalidates the one its owner is about to use.

**Background sending.** The email is sent after the `202` response. If delivery fails, it is logged by user id and the person simply asks again; the response never changes.

## Rate limits

Fixed-window counters in the `rate_limit_counters` table, keyed by `sha256(scope:value)` so no address or IP is stored in clear. They hold across restarts and across any number of replicas, because each attempt is one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING count`. Counters older than a day are deleted as new attempts arrive.

| Scope | Default | Applies to |
|---|---:|---|
| `login_ip` | 20 per 15 min | every login request from one client IP, checked before validation |
| `login_email` | 5 per 15 min | login requests for one normalized address |
| `verify_ip` | 30 per 15 min | every verify attempt from one client IP |

Verification is limited per IP only: the email is unknown until the token is looked up, and a 256-bit token cannot be guessed anyway. Over the limit the response is `429` with `Retry-After` and the body `Too many requests. Try again later.` A fixed window can allow up to twice the limit across a window boundary.

The client IP is `request.client.host`. For the per-IP limits an IPv6 address is reduced to its `/64` network (an IPv4-mapped address to its IPv4 address), because one subscriber usually holds a whole `/64` and could otherwise rotate addresses to escape the limit; the cost is that clients sharing a `/64` share the budget. Behind a proxy, uvicorn only trusts `X-Forwarded-For` from `FORWARDED_ALLOW_IPS`, so staging must set it to the BFF or ingress address, and the BFF must forward the browser's IP; otherwise every request counts against the proxy's IP.

## Audit and logging

`auth_events` is append-only (a trigger rejects `UPDATE`, `DELETE` and `TRUNCATE`, as for `audit_events`). It records `login_requested`, `login_succeeded`, `login_failed` (reason `unknown`, `expired`, `used` or `revoked`), `logout` and `rate_limited` (reason = scope; written once per key and window, on the first denied request, so hammering cannot grow the append-only table), with user id, session row id and client IP. It never holds a token, a session id cookie value or a full address: `email_masked` (`a***@example.com`) is filled only for a per-email rate limit, where no user id is used. `user_id` has no foreign key so the trail stays intact.

Application logs follow [docs/logging.md](logging.md) and carry `user_id` and `session_id` (the row id) only. The shared formatter redacts fields named like `token` or `cookie`, but it does not recognise email addresses, so the service never passes an address, token or cookie value to a logger, and an SMTP failure is logged by exception type only. `test_logging_redaction.py` runs a full flow and checks the captured JSON.

## Email provider setup (staging)

Any SMTP provider works (for example a transactional-mail service's SMTP relay). For a hosted environment:

1. Verify the sending domain with the provider and choose `IDENTITY_EMAIL_FROM` on it.
2. Create an SMTP credential scoped to sending only.
3. Store `IDENTITY_SMTP_USERNAME` and `IDENTITY_SMTP_SECRET` in the deployment secret store (GitHub environment secrets or the platform's secret manager). **Never commit them**, and never put them in `infra/compose.yaml` or an image.
4. Set `IDENTITY_SMTP_HOST`, `IDENTITY_SMTP_PORT` and either `IDENTITY_SMTP_STARTTLS=true` (usually port 587) or `IDENTITY_SMTP_SSL=true` (usually 465).
5. Set `IDENTITY_LOGIN_LINK_URL` to the public HTTPS URL of the confirm page, `LEDGERMESH_ENV=staging`, `IDENTITY_OPERATOR_EMAILS`, and `FORWARDED_ALLOW_IPS`.
6. Run migrations (`alembic -c services/identity/alembic.ini upgrade head`, or `RUN_MIGRATIONS=true` with the LM-047 image built with `SERVICE=identity PORT=8005`).

## Local workflow with Mailpit

[Mailpit](https://mailpit.axllent.org/) is a local SMTP server with a web inbox; nothing leaves your machine.

```bash
make infra-up                      # includes identity-db, mailpit and identity
make mail-ui                       # prints http://localhost:8025

curl -i -X POST http://localhost:8005/v1/auth/login-requests \
  -H 'Content-Type: application/json' -d '{"email":"alice@example.com"}'
```

Open the inbox at <http://localhost:8025>, click the link, and press **Sign in to LedgerMesh**. The browser now holds `lm_session` for `localhost`; `http://localhost:8005/v1/me` shows the user. Sign in as `operator@example.com` (the Compose default for `IDENTITY_OPERATOR_EMAILS`) to see `/v1/operator/auth-events`.

To run only the service on the host against the Compose database and Mailpit: `make run-identity`. The automated end-to-end check (request, read the email through Mailpit's API, verify, replay, logout) is `make identity-e2e`; repeated runs within 15 minutes can hit the per-address limit for the operator address.

## What remains

- **LM-011 (web UI, PR #97):** the BFF should proxy `/api/auth/*` to the Identity Service (same-site), forward the browser's `Cookie` header and client IP, call `GET /v1/sessions/introspect` for features that need a principal, and add a sign-in form that posts JSON to the login-request endpoint. Locally, cookies are not isolated by port, so a cookie set by `localhost:8005` is also sent to `localhost:8080`.
- **LM-051 (#63, public/guest experience):** add a sign-in entry point to the landing page while keeping the guest demo exactly as it is.
- **LM-048 (#56, hosted staging):** hosted cookies require HTTPS and a single same-site public entry point; `/v1/auth/*` should be reached through it, and `/v1/sessions/introspect` stays on the private network. Optionally add a shared-key header for introspection callers.
- **LM-047 images:** add `identity:identity:8005` to `make images-build`/`images-check` and the image workflow when the service is deployed.
- **LM-042 security:** the shared safe-error handler and internal-route gating; the identity service already has its own validation handler that does not echo input. Adding `email` to the shared log-redaction list is a possible follow-up.
